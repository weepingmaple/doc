## Token-handling changes

### Missing token

The backup extracts the token type too early:

```python
access_token = x_helper.get_access_token_from_cookie(headers)
note_type = x_helper.get_type_from_token(access_token)

if not access_token:
    return x_helper.redirect(x_helper.landing_url)
```

If `get_type_from_token()` cannot handle a missing token, the function could fail before reaching its intended redirect. `index.py` avoids this ordering problem by checking `if not access_token` first. Whether the backup actually fails depends on the helper implementation, which was not included.[^1_1][^1_2]

### Invalid or expired token

The new script introduces this branch:

```python
safe_note_type = x_helper.get_type_from_token_safe(access_token)

if safe_note_type:
    timeout_url = x_helper.timeout_error_url(safe_note_type)
    return x_helper.redirect(timeout_url)
else:
    return x_helper.redirect(x_helper.landing_url)
```

The intended behavior is:


| Token condition | Backup behavior | New behavior |
| :-- | :-- | :-- |
| Missing | Landing redirect, provided the earlier extraction does not fail | Landing redirect without attempting type extraction |
| Expired, with recoverable type | Type-specific timeout, provided extraction succeeds | Type-specific timeout |
| Malformed or otherwise invalid, with no recoverable type | Depends on the original extraction helper | Landing redirect, provided the new safe helper handles the token without raising |
| Valid | Update user request ID and forward to origin | Same |

The new fallback is useful, but the word “safe” in the helper name is not proof of its behavior. Its implementation must be checked.[^1_2][^1_1]

## Issues to verify

1. **Dependency:** `index.py` requires `x_helper.get_type_from_token_safe()`. If that function is absent from the deployed helper module, requests entering the invalid-token branch will fail. Neither uploaded file contains its implementation.[^1_2]
2. Token-type handling: The invalid-token branch still reads a type from a rejected token. Verify that the helper tolerates malformed input and that any recovered type is restricted to supported values before constructing the timeout URL. It should serve only redirect selection—not authorization.[^1_2]
3. Unused assignment: In the new valid-token path, `note_type = x_helper.get_type_from_token(access_token)` is assigned but never used afterward. Unless that call intentionally performs additional checks, it is redundant and adds another possible failure point.[^1_2]
4. Shared submit authorization gap: Neither script explicitly checks `payload['allowed']` or the stored user's `Allowed` value in `submit_handler()` before forwarding to origin. If this handler is intended to enforce admission, verify where that authorization happens; token validity alone is not an explicit admission check in these files.[^1_1][^1_2]
5. Shared user-record assumption: Both scripts assume the decoded payload contains `uuid` and that `get_user_by_id()` returns a mutable user record. Neither shows handling for a missing UUID or missing user. The actual failure behavior depends on the helpers.[^1_1][^1_2]
6. Logging scope: Request-ID prefixes were added to the submit handler’s explicit messages, not throughout the script. Both versions still log the full incoming event and request; review what cookie or token data those logging helpers expose.[^1_1][^1_2]

## Deployment assessment

`index.py` is the better starting point because it fixes the premature token-type extraction and improves submit-request diagnostics. However, I would treat it as a targeted robustness change—not a complete security fix—until the new helper and the submission authorization path are verified.[^1_1][^1_2]

Before deploying, test these cases against the actual helper modules:


| Test | Expected result or check |
| :-- | :-- |

| Expired token with a supported type | Type-specific timeout redirect |

| Valid token and existing user | Update `RequestId`, then return the original request |
| Valid token but missing user | Verify deliberate handling rather than assuming a record exists |
| Valid token with `allowed='false'` | Confirm the intended admission policy is enforced somewhere |

# Focus on the Token-handling changes.

`index.py` makes two main token-handling changes in `submit_handler()`: it checks whether a token exists before extracting its type, and it adds a fallback redirect when an invalid or expired token has no recoverable type. The successful-token flow remains essentially unchanged.[^2_1][^2_2]

## 1. Processing order

The backup follows this sequence:

```text
Read token from cookie
→ Extract note_type
→ Check whether token exists
→ Check whether token is invalid or expired
→ Decode payload and update user
```

The new script follows:

```text
Read token from cookie
→ Check whether token exists
→ Check whether token is invalid or expired
   → If rejected: attempt safe type extraction and redirect
→ If accepted: extract note_type
→ Decode payload and update user
```

The important distinction is that the new script delays the normal `get_type_from_token()` call until after the token passes the validation helper. It still attempts a separate type extraction on rejected tokens, solely to choose the redirect destination.[^2_2][^2_1]

## 2. Missing-token handling

### Backup

```python
access_token = x_helper.get_access_token_from_cookie(headers)
note_type = x_helper.get_type_from_token(access_token)

if not access_token:
    return x_helper.redirect(x_helper.landing_url)
```

The problem is the ordering: `get_type_from_token()` receives the token before the function checks whether it is missing. If that helper raises on `None` or an empty value, the intended landing-page redirect is never reached. The helper implementation is not provided, so this is a potential failure—not a confirmed runtime error.[^2_1]

### New script

```python
access_token = x_helper.get_access_token_from_cookie(headers)

if not access_token:
    # Log missing-token reason and request ID
    return x_helper.redirect(x_helper.landing_url)
```

This branch returns without attempting token-type extraction. It is a clear improvement for missing-cookie requests, regardless of whether the original helper already tolerated empty input.[^2_2]

## 3. Rejected-token handling

| Aspect | `index_bak.py` | `index.py` |
| :-- | :-- | :-- |
| Type extraction | Uses `get_type_from_token()` before validation | Uses `get_type_from_token_safe()` after rejection |
| Recoverable type | Redirects to its timeout page | Redirects to its timeout page |
| No recoverable type | No explicit fallback in the handler | Redirects to the landing page |
| Diagnostics | No dedicated rejection log | Logs rejection, selected destination, and request ID |
| Helper dependency | Existing extraction helper | Adds a new safe-extraction helper |

These differences apply to the shared “invalid or expired” branch; the new script does not separately distinguish the two conditions.[^2_1][^2_2]

The new logic is:

```python
if x_helper.token_invalid_or_expired(access_token):
    safe_note_type = x_helper.get_type_from_token_safe(access_token)

    if safe_note_type:
        return x_helper.redirect(
            x_helper.timeout_error_url(safe_note_type)
        )

    return x_helper.redirect(x_helper.landing_url)
```

For example, an expired token whose type can still be recovered as `fit` goes to `timeout_error_url('fit')`. A malformed token from which the safe helper returns no type goes to the landing page. Both outcomes depend on the safe helper behaving as intended.[^2_2]

### What “safe” does not establish

Neither uploaded file defines `get_type_from_token_safe()`. Therefore, the comparison cannot confirm whether it catches decoding errors, verifies authenticity, accepts expired tokens, or restricts the returned type to supported values. The handler itself only checks whether the result is truthy.[^2_2]

Also, neither handler wraps `token_invalid_or_expired()` in exception handling. If that helper raises on malformed input instead of returning `True`, execution never reaches the new fallback. Consequently, the new code improves the intended control flow but does not, by itself, prove that every malformed token is handled gracefully.[^2_1][^2_2]

## 4. Accepted tokens and scope

After validation passes, the new script performs:

```python
note_type = x_helper.get_type_from_token(access_token)

payload = x_helper.decrpt_jwt_token(access_token)
user_item = dynamodb_helper.get_user_by_id(payload['uuid'])
user_item['RequestId'] = cf_request_id
dynamodb_helper.create_or_update_user(user_item)

return request
```

The payload decoding, user lookup, `RequestId` update, and forwarding to origin are unchanged. However, the new `note_type` variable is not subsequently used in `submit_handler()`, making that extraction apparently redundant unless the helper intentionally performs an additional check.[^2_1][^2_2]

These changes do not introduce token renewal, alter JWT generation, change expiry calculation, or modify token handling in `lny_handler()`. They also do not add an explicit `allowed` check to the submit path.[^2_2][^2_1]

The most important verification is therefore the helper contract: `get_type_from_token_safe()` must exist and handle rejected tokens predictably, while `token_invalid_or_expired()` must reliably reject bad input without preventing the fallback from running. Those implementations are needed to confirm the robustness of the new behavior.[^2_2]

# Write a report for the application team to understand this change and why there is 302

The token-handling change makes submission requests with missing, invalid, or expired tokens follow a more controlled redirect path. An HTTP 302 indicates a temporary redirect to the landing or timeout page—not, by itself, an application failure or a successful submission.[^3_1][^3_2]

## Change report

**Audience:** Application team\
Date: 5 October 2026\
Files compared: `index_bak.py` and `index.py`\
Change scope: Token handling and diagnostic logging in `submit_handler()`.[^3_3][^3_1]

### Purpose

The change addresses an ordering issue in the backup script: it attempts to extract `note_type` before checking whether the access token exists or passes validation. The updated script checks token presence first, then validates it, and introduces a fallback destination when a rejected token has no recoverable type.[^3_1][^3_3]


| Area | Previous behavior | Updated behavior |
| :-- | :-- | :-- |
| Missing token | Attempts type extraction before the missing-token check | Redirects to landing without type extraction |
| Invalid or expired token | Uses a type extracted before validation to select the timeout page | Attempts safe type extraction after rejection |
| No recoverable type | No explicit fallback in the submit handler | Redirects to landing |
| Valid token | Decodes payload, updates user `RequestId`, returns request | Same processing, with normal type extraction moved after validation |
| Logging | Generic submit messages | Request ID, rejection reason, and redirect destination |

The waiting-room token logic in `lny_handler()` is unchanged.[^3_3][^3_1]

## Why HTTP 302 occurs

HTTP `302 Found` tells the client to make another request to the URL specified in the response’s `Location` header. Browsers normally follow this redirect automatically.[^3_2]

In these scripts, rejected submission requests return the result of:

```python
return x_helper.redirect(destination_url)
```

rather than returning the original CloudFront request. The selected destination depends on the token condition.[^3_1][^3_3]


| Condition in updated submit handler | Destination | Meaning |
| :-- | :-- | :-- |
| Access token is missing | `x_helper.landing_url` | The request has no token to validate |
| Token is invalid or expired, and a type is recovered | `x_helper.timeout_error_url(safe_note_type)` | The request is rejected and sent to a type-specific timeout page |
| Token is invalid or expired, and no type is recovered | `x_helper.landing_url` | The request is rejected and uses the fallback page |
| Token passes validation | Original request is returned | Processing continues; this branch does not explicitly issue a redirect |

These are the destinations visible in `index.py`.[^3_1]

### Important verification boundary

The uploaded files do not include the implementation of `x_helper.redirect()`. Therefore, they confirm the redirect decisions, but they do not independently confirm that the helper returns status `302` or show its exact response headers. The team should verify that helper or inspect the actual response. AWS’s Lambda@Edge redirect examples use status `302` with a `Location` header.[^3_4][^3_3][^3_1]

For a viewer-request Lambda@Edge association, a generated response is returned directly to the viewer instead of forwarding that original request to origin. Consequently, an edge-generated redirect can explain why the application receives no corresponding submission request. The deployed trigger association must be checked to confirm this applies here.[^3_5]

## What changed about redirects

The change does **not** introduce redirects for the first time. The backup already redirected missing-token requests to landing and invalid/expired-token requests to timeout. The update changes the processing order and adds a fallback for a rejected token whose type cannot be recovered.[^3_3][^3_1]

Two scenarios explain the operational difference:

- Missing cookie: Previously, type extraction ran first and could raise before the landing redirect if the helper did not tolerate an empty token. Now the handler reaches the landing redirect without that extraction call.[^3_3][^3_1]
- Malformed token: Previously, normal type extraction could fail before validation. Now validation runs first, followed by the safe-extraction fallback if validation returns rejection. This produces a controlled redirect only if both helpers handle the input without raising.[^3_1][^3_3]

A rise in 302 responses after deployment could therefore represent previously failing requests now reaching an intended redirect branch. However, the code comparison alone does not establish that this happened; request logs and response evidence are needed.

The new logs group “invalid or expired” together. A timeout-page redirect therefore does not prove that expiry was the specific rejection reason.[^3_1]

## Application impact

### Submission is not confirmed

When the handler takes a token-rejection branch, it returns before payload decoding, user lookup, and the `RequestId` update. A redirect from that branch must not be treated as confirmation that the form submission completed.[^3_1]

If the original submission is a `POST`, browsers following a 302 generally make a `GET` request to the destination. The form body is not replayed as a POST to the landing or timeout page.[^3_2]

### Redirect following can hide the rejection

The client may receive a 302 and then load a landing or timeout page successfully. The team should inspect the original submission response and redirect chain, rather than judging submission success solely from the final page’s status. This follows from the browser’s automatic redirect behavior.[^3_2]

### Valid-token behavior is unchanged

For accepted tokens, the handler still decodes the payload, retrieves the user, updates `RequestId`, and returns the original request. It does not explicitly return a 302 in that branch; any later redirect must be investigated separately.[^3_3][^3_1]

## Verification and acceptance

The application and cloud teams should validate the following before closing the change:


| Check | Expected evidence |
| :-- | :-- |
| Redirect helper | Confirm `x_helper.redirect()` returns the intended status and `Location` header |
| Missing-token request | Landing redirect; no token-type extraction |
| Expired token with recoverable type | Type-specific timeout redirect |
| Malformed token | Controlled rejection rather than an unhandled exception |
| Rejected token with no recoverable type | Landing fallback |
| Valid token and existing user | User `RequestId` update and original request returned |
| Browser submission | Original response, redirect destination, and follow-up request method captured |
| Deployment association | Confirm whether the function runs on viewer request |
| Log correlation | Match `CF Req ID:[...]` to the rejection and destination messages |

The handler-level expectations come from `index.py`; the actual 302 response and edge behavior require verification of the helper and deployed CloudFront association.[^3_4][^3_5][^3_1]

The main unresolved dependency is `get_type_from_token_safe()`: it must exist in the deployed helper module and handle rejected tokens predictably. Neither uploaded script shows its implementation or guarantees that the validator catches malformed-token errors.[^3_1]

For incident classification: a token-related 302 to the intended landing or timeout page is an expected rejection outcome. A 302 with a supposedly valid token, an incorrect destination, or a redirect loop requires investigation—not automatic classification as either a successful submission or an origin failure.[^3_2][^3_1]

# the bak script is the older version. I want to tel the application team understand the new change and also why it would help with the 503 error

The new `index.py` can help reduce HTTP 503 errors caused by token-processing exceptions: it checks for a missing token before extracting token fields and adds a fallback redirect for rejected tokens. This is a targeted mitigation—not a confirmed fix for all 503 errors—and its effectiveness depends on the helper implementations and the actual error logs.[^4_1][^4_2][^4_3]

## Application team report

Subject: Token-handling update to reduce submission-related HTTP 503 errors

The older version, `index_bak.py`, attempted to extract the token’s `note_type` before checking whether the access token existed or was valid. The new version, `index.py`, changes this sequence so that missing tokens are handled immediately, and invalid or expired tokens follow a dedicated rejection path.[^4_2][^4_1]

The purpose is to handle unusable tokens as an expected application condition—redirecting the user to the landing or timeout page—rather than allowing token-processing errors to interrupt the Lambda@Edge execution. AWS documents that unhandled exceptions in Lambda@Edge code can result in HTTP 503 responses from CloudFront.[^4_3][^4_2]

## Previous failure risk

The older script executes:

```python
access_token = x_helper.get_access_token_from_cookie(headers)
note_type = x_helper.get_type_from_token(access_token)

if not access_token:
    return x_helper.redirect(x_helper.landing_url)

if access_token and x_helper.token_invalid_or_expired(access_token):
    return x_helper.redirect(x_helper.timeout_error_url(note_type))
```

The key issue is that `get_type_from_token()` runs before the missing-token check and validation. If the token is absent or malformed and the extraction helper raises an exception, execution stops before the intended redirect can be returned. The uploaded files do not contain this helper’s implementation, so this remains a plausible failure path rather than a confirmed root cause.[^4_1]

The potential chain is:

```text
Submission contains a missing or malformed token
→ Token-type extraction raises an unhandled exception
→ Lambda@Edge execution fails
→ CloudFront returns HTTP 503
```

AWS identifies unhandled function exceptions as a cause of Lambda@Edge execution errors and HTTP 503 responses. Confirming this chain for the application requires the corresponding exception in CloudWatch logs.[^4_4][^4_3]

## New handling and benefit

The updated script checks token presence before attempting normal type extraction:

```python
access_token = x_helper.get_access_token_from_cookie(headers)

if not access_token:
    return x_helper.redirect(x_helper.landing_url)

if x_helper.token_invalid_or_expired(access_token):
    safe_note_type = x_helper.get_type_from_token_safe(access_token)

    if safe_note_type:
        return x_helper.redirect(
            x_helper.timeout_error_url(safe_note_type)
        )

    return x_helper.redirect(x_helper.landing_url)
```

This changes the handling as follows.[^4_2]


| Token condition | Older version | New version | How it helps |
| :-- | :-- | :-- | :-- |
| Missing token | Calls type extraction before checking presence | Immediately redirects to landing | Removes the premature extraction call that could fail on an empty token |
| Invalid or malformed token | Calls normal type extraction before validation | Validates first, then attempts safe extraction for redirect selection | Can avoid an extraction exception, provided the helpers handle bad input correctly |
| Expired token with recoverable type | Redirects to the type-specific timeout page if earlier extraction succeeds | Uses safe extraction to select the timeout page | Makes rejected-token handling explicit |
| Rejected token without recoverable type | No explicit fallback in the submit handler | Redirects to landing | Provides a defined fallback instead of assuming a usable type |
| Valid token | Decodes payload, updates user `RequestId`, returns request | Same successful processing | Preserves the accepted-token path |

The new script also logs the CloudFront request ID, token-rejection condition, and redirect destination. These messages make it easier to correlate a reported submission failure with the handler’s decision.[^4_2]

### Why a 302 is preferable here

When the token cannot be used, the intended outcome is a controlled redirect—not successful form submission. HTTP 302 represents a temporary redirect to the destination in the `Location` header; it is different from an HTTP 503 execution failure.[^4_5]

The expected improvement is therefore:

```text
Before, for affected requests:
Token-processing exception → Lambda execution failure → 503

After, when handled successfully:
Missing or rejected token → Landing/timeout redirect → 302
```

This does not “convert every 503 into a 302.” It prevents specific token-related failure paths and returns the intended redirect instead. The actual 302 status must be verified in `x_helper.redirect()`, whose implementation was not provided.[^4_3][^4_1][^4_2]

## Limitations and dependencies

The change should not be described as a complete 503 fix for the following reasons:

- The safe helper must exist. `get_type_from_token_safe()` is a new dependency; if it is missing or raises an exception, the rejected-token branch can still fail.[^4_2]
- Validation must tolerate malformed input. The new handler does not catch exceptions from `token_invalid_or_expired()`. If validation raises rather than returning a rejection result, the fallback is not reached.[^4_2]
- Successful-token processing can still fail. Payload decoding, user lookup, and the DynamoDB update remain in the accepted-token path without handler-level exception handling.[^4_1][^4_2]
- Other 503 causes remain unaffected. Origin unavailability, Lambda@Edge throttling, and function timeouts can also produce 503 responses; this token-handling change does not directly resolve them.[^4_6]

The token-handling changes apply to `submit_handler()`. Token processing in `lny_handler()` remains unchanged.[^4_1][^4_2]

## Validation and acceptance

To establish that this change addresses the reported issue:

1. Check pre-change CloudWatch logs for exceptions associated with token-type extraction, and correlate them with the affected CloudFront requests. AWS recommends examining regional Lambda@Edge logs to identify execution failures.[^4_4]
2. Confirm that `get_type_from_token_safe()` exists in the deployment and returns a controlled result for malformed, expired, and otherwise rejected tokens.[^4_2]
3. Test missing-token and rejected-token submissions; verify the intended landing or timeout redirect and the absence of unhandled exceptions.[^4_2]
4. Test a valid-token submission; confirm that the user’s `RequestId` is updated and the original request continues normally.[^4_2]
5. Compare token-related execution errors and 503 responses before and after deployment, rather than treating an increase in redirects alone as proof of resolution. CloudFront and Lambda@Edge error logs support this distinction.[^4_7][^4_4]

Recommended wording for the change record:

> Updated submission token handling to check token presence before extracting token fields and to provide a fallback redirect for invalid or expired tokens. This is intended to reduce Lambda@Edge execution failures—and associated HTTP 503 responses—caused by unusable tokens. Missing or rejected tokens should receive a controlled landing-page or timeout-page redirect instead. Root-cause confirmation and post-deployment validation are required; the change does not address unrelated origin, timeout, or throttling errors.[^4_6][^4_3][^4_1][^4_2]

| Missing token | Redirects to landing, but attempts token-type extraction first | Checks for the missing token and redirects immediately |
| Invalid or expired token | Redirects to a type-specific timeout page using the previously extracted type | Attempts safe type extraction, then redirects to the timeout page |
| Rejected token with no recoverable type | No explicit fallback | Redirects to landing |
| Diagnostics | Generic messages | Adds request ID, rejection reason, and redirect destination |

These changes improve how the handler reaches its existing redirects and add a fallback destination.[^5_2][^5_1]

## Why it can help with 503

The older script could fail during token-type extraction before reaching its intended redirect. The enhancement removes that premature extraction for missing tokens and provides a more controlled path for rejected tokens. It can therefore reduce token-related exceptions, provided the validation and safe-extraction helpers handle malformed input correctly.[^5_1][^5_2]

A concise explanation for the application team:

> Redirect handling already existed in the original script. The new version enhances token validation order, fallback handling, and logging so that requests with unusable tokens are more likely to reach the intended redirect instead of failing during token processing. This is intended to reduce token-related 503 errors; it is not a new redirect feature or a fix for every 503.[^5_2][^5_1]
